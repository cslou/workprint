### Observed execution identity limitation (historical blocker)

The native modern send path makes an important distinction:

- `sendMessage` acknowledges native execution `runId` and an accepted `signal.id`.
- Its input is saved as native `role:'signal', type:'user'`, with that signal/message ID and native signal metadata; it is not a saved `role:'user'` row. The accepted navigation text projection currently admits only user/assistant rows and must not silently treat every signal as user text.
- The native stream's assistant message ID matches the saved assistant message. Input/assistant IDs, conversation/resource IDs, text and order survive process restart through native `thread-history` with **zero provider calls**.
- The execution `runId` is absent from saved native messages, reloaded history and native thread records. A supplemental public `getThreadById` read found empty thread metadata before and after restart. Public `getWorkflowRunById` and both built-in workflow snapshot reads return `null` after terminal settlement, before and after restarting the built process over the same Postgres store.

This was reproduced in two initial trials and two supplemental thread-record trials with `shouldPersistSnapshot:()=>true`, each pair using `cleanupTimeoutMs:60000` and `cleanupTimeoutMs:0` (manual registry cleanup). All four built processes exited 0 in about 3.6–3.7 seconds; reloads preserved exact message IDs/text and made no provider call. All four probes then failed the explicit durable execution/turn identity assertion (exit 1), not setup or message persistence.

The pinned public `DurableAgentConfig` describes snapshot policy for in-flight crash recovery and cleanup grace for registry entries. Inspection of the shipped 1.79.0 implementation confirms deliberate deletion of both built-in agent workflow snapshots after non-suspended terminal outcomes, independently of the snapshot predicate. Internal implementation was read, never called or modified. No inspected public retention control changes this outcome.

**Initial recommendation, resolved for Story 4:** pause dependent turn bindings/client delivery until the orchestrator resolves the approved meaning of persisted turn identity. Main-owned clarification `9319d230866112d8c4dc997bc51c1d9cefb1a245` now requires persisted native input-signal/message and assistant-message identities, conversation/resource identity and exact text/order, not terminal execution-ID retention. The four failed probes remain evidence of the actual limitation, not passes or execution/message-ID aliases. If terminal execution `runId` must survive reload, the tested native path does not meet that criterion. Do not reinterpret a signal/message ID as an execution-turn ID, reconstruct identity from event order, retain transient cache as canonical history, introduce an alternate ledger/workflow wrapper or patch native schema/vendor code to force proof. Either explicitly approve a narrower contract that persists message/signal/conversation identities while execution IDs remain transient, or separately qualify a native capability that supplies the required retained identity. No dependency upgrade, release-age exception or AC/planning change was made here.

## Bounded official-SDK api-client facade

`packages/api-client/src/native-turns.ts` uses the official `sendMessage` and `subscribeToThread`/`processDataStream`, without SSE framing/parsing or reconnect/retry. Send acknowledgment exposes the actual execution `runId` separately from the native input message/signal ID. Observation is established before send; consumption names that actual execution ID and ignores other executions, never a latest-thread approximation. A validated native stop exposes the native assistant message ID as **observed**, not a saved-completion acknowledgment; authoritative reload must correlate the exact ID separately. Only text deltas and those IDs leave the facade, not native errors/stacks/context/usage/metadata. Error, tripwire, interrupted output and missing terminal results cannot become completion.

Client limits are 3 s for token/send/subscription establishment, 9 s for observation, 8192 UTF-8 input/output text bytes and 1 MiB raw response/stream bytes. A shorter existing client deadline tightens these bounds. Cancellation/close ends observation and clears its timer/caller listener; it sends no Stop and does not claim server cancellation. Legacy no-input calls remain local unavailable results and Stop remains unavailable. The browser has no new chat consumer or enabled Send.

`native-turn-client.test.ts` independently drives the api-client with both real accounts through the built server/native Postgres, including exact Unicode/whitespace/ID reload, errors/incomplete output/caps/native deadlines, no-effect rejections and production unavailability.
