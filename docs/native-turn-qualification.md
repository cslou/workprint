## Actual native observations before adapters

Local redacted evidence: `/tmp/workprint-sprint-004/native-turn-transport/`. The probe uses actual isolated GoTrue/Auth and native PostgreSQL, two synthetic accounts, the supported conversation fixture, public `mastra.addAgent`, official client-js 1.56.0 and the native Hono routes. - `Agent.stream` returned HTTP 200 `text/event-stream`. The official `processDataStream` callback observed native `start`, `step-start`, `text-start`, `text-delta`, `text-end`, `step-finish` and `finish` parts.
- Native `start.runId` identifies execution; `start.payload.messageId` / final message identity matched the assistant ID subsequently read from native Postgres. User/assistant text, native message IDs, thread/resource IDs and chronology were observed directly. Native `sendMessage` returned `{accepted:true, runId, signal:{id,type,contents,...}}`.
- A supported durable Agent with `shouldPersistSnapshot` configured yielded matching native `durable-agentic-execution` / `durable-agentic-loop` run IDs and successful snapshots immediately after normal completion. A later 250 ms read did not retain those rows. The follow-up below reproduces the terminal identity gap across a process restart; transient snapshots do not prove durable reload.
- A controlled 2.5-second provider wait completed in roughly 2.7 seconds and saved both messages in full through the built HTTP server. This is a probe showing execution can outlast the two-second body-intake deadline, not the final permanent boundary test.
- Native `TokenLimiterProcessor({limit:64,strategy:'abort'})` allowed 64 single-character text-delta contributions and saved the full assistant response. A 65th contribution emitted a native `tripwire` after 64 visible characters and saved only the user message. This probes the native estimated-token control; it is not a universal provider-token or byte-cap claim. An immediate over-cap workflow snapshot remained `running`; settlement/release was unqualified at that initial checkpoint. The follow-up below uses an open provider stream and bounded cleanup observations.
- Raw provider failure produced a native error part and `finish.stepResult.reason:'error'`. Persistence retained an assistant **error part**, not a normal empty text completion; flattening it to text would lose that evidence. The existing read-only text navigation projection correctly does not treat unsupported parts as successful text history.
- A provider that closed without its terminal parts was normalized by the unguarded native path into `reason:'stop'` and saved assistant text. This is a genuine integrity hazard. A supported `processLLMResponse` processor checking the observed native `step-finish` / stop outcome emitted a native tripwire and prevented that incomplete assistant from being saved. The guard remains probe-only until permanent tests qualify it with all failure/boundary cases.

### Blocking execution identity gap

The native modern send path makes an important distinction:

- `sendMessage` acknowledges native execution `runId` and an accepted `signal.id`.
- Its input is saved as native `role:'signal', type:'user'`, with that signal/message ID and native signal metadata; it is not a saved `role:'user'` row. The accepted navigation text projection currently admits only user/assistant rows and must not silently treat every signal as user text.
- The native stream's assistant message ID matches the saved assistant message. Input/assistant IDs, conversation/resource IDs, text and order survive process restart through native `thread-history` with **zero provider calls**.
- The execution `runId` is absent from saved native messages, reloaded history and native thread records. A supplemental public `getThreadById` read found empty thread metadata before and after restart. Public `getWorkflowRunById` and both built-in workflow snapshot reads return `null` after terminal settlement, before and after restarting the built process over the same Postgres store.

This was reproduced in two initial trials and two supplemental thread-record trials with `shouldPersistSnapshot:()=>true`, each pair using `cleanupTimeoutMs:60000` and `cleanupTimeoutMs:0` (manual registry cleanup). All four built processes exited 0 in about 3.6–3.7 seconds; reloads preserved exact message IDs/text and made no provider call. All four probes then failed the explicit durable execution/turn identity assertion (exit 1), not setup or message persistence.

The pinned public `DurableAgentConfig` describes snapshot policy for in-flight crash recovery and cleanup grace for registry entries. Inspection of the shipped 1.79.0 implementation confirms deliberate deletion of both built-in agent workflow snapshots after non-suspended terminal outcomes, independently of the snapshot predicate. Internal implementation was read, never called or modified. No inspected public retention control changes this outcome.

**Recommendation:** pause dependent turn bindings/client delivery until the orchestrator resolves the approved meaning of persisted turn identity. If terminal execution `runId` must survive reload, the tested native path does not meet that criterion. Do not reinterpret a signal/message ID as an execution-turn ID, reconstruct identity from event order, retain transient cache as canonical history, introduce an alternate ledger/workflow wrapper or patch native schema/vendor code to force proof. Either explicitly approve a narrower contract that persists message/signal/conversation identities while execution IDs remain transient, or separately qualify a native capability that supplies the required retained identity. No dependency upgrade, release-age exception or AC/planning change was made here.
