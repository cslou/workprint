# Native workflow process-recovery qualification

This is private/local, separately built test qualification, not a production intent endpoint, application/business ledger, generation/export pipeline or authorization to run a provider. [Independent execution and bounds](native-workflow-qualification.md) and the distinct [conversation identity/observation limits](native-turn-control.md) remain binding. Native technical success is not human approval.

## One native owner and stable hand-off

The isolated harness setup role creates only `qualification.intent` and `qualification.effect`. An intent commits a logical UUID, a stable native run UUID, the verified account/resource UUID, the selected controlled boundary and original timestamps/deadlines. It carries no application workflow status. The serving role has only fixture DML/USAGE; its actual attempt to prepare a schema fails. Native initialization remains exclusively supported `PostgresStore.init()`, with no native schema/row/vendor patch.

A separately compiled entry registers one qualification workflow alongside the controlled native assistant, then uses the existing app-owned server, real Auth and native Postgres. Before native startup recovery, it restores at most two ephemeral permits and only the remaining original five-second wait/ten-second run budgets. Permits, dispatch markers and in-flight request coalescing are resource bookkeeping, never native identity/status/ownership or a recoverable execution ledger. Terminal release still requires the exact actual persisted outcome; cancellation acknowledgment alone remains insufficient.

Narrow reconciliation is an explicit bounded hand-off over a bounded fixture-intent page. Missing/pending work starts through public `createRun({runId, resourceId})`/`startAsync()` on the committed identity. Running/waiting work is re-entered only through public native `Run.restart()`, which honors native ownership. Concurrent account-scoped requests coalesce without disclosing another account's results. Locally dispatched work is not re-sent. Repeated terminal reconciliation reads native results; it neither creates another run nor re-executes completed work. There is no application polling scheduler, second execution owner or ownership repair.

The real existing startup `restartAllActiveWorkflowRuns()` is invoked once and delegated unchanged. It may skip a still-owned run and arrange its own lease recheck. A separate no-explicit-reconciliation case exercises that actual sweep; a missed fixture wait remains honestly canceled by the original bound rather than silently extending recovery time. The explicit qualification hand-off makes three bounded calls, waiting once for the *observed native lease expiry*, never retrying until green.

## Observed native constraints and required safeguards

- **Stable graph identities:** native `.sleep()`/`.sleepUntil()` needs an explicit supported stable `id` when it must survive process reconstruction. Generated IDs can change between processes. A failed unconfigured probe is retained; the qualification graph uses `recovery-sleep` and fixed step IDs. Entry/bootstrap and compiled recovery-module hashes are equal before and after every process restart.
- **Ownership latency is configured, not assumed:** the native default lease is 15 seconds. The separately built fixture explicitly uses the documented `MASTRA_AGENT_THREAD_LEASE_TTL_MS=1000`; renewal and boot recheck remain native behavior. This is not a default, production or multi-process latency/capacity claim. Native lease jitter can outlast a shorter fixture bound, so automatic recovery is not promised to complete before that bound.
- **Canonical resource identity:** generic native boot recovery can enter a step without a `resourceId` in the in-memory execution context. The saved native row retains its resource identity. The fixture validates its exact run/workflow/resource against public native storage and the trusted committed intent before a local SQL effect; it never infers ownership from caller claims, a permit or a missing execution-context field.
- **Guarded repetition, not exactly-once execution:** the fixture effect uses one atomic unique-key `INSERT ... ON CONFLICT DO NOTHING`. A real process kill after its commit but before native step acknowledgment causes actual step re-entry in another process, with insert counts `1, 0` and one saved effect. Removing the guard produces a native failed outcome on repeated insertion, not success. An external provider needs its own authorization, idempotency, uncertainty and publication/cancellation proof; this SQL fixture does not qualify automatic replay of uncertain provider work.
- **Conversation commands are separate:** the lost-start-ack matrix also kills a genuinely in-flight controlled conversation call. Restart/reconciliation creates zero new model calls and retains the same single saved input-signal ID. Saved signal identity is not an execution ID or a retained terminal execution-status promise. Durable-agent recovery remains opt-in/off; workflow recovery must not replay conversation commands.

## Actual process matrix and evidence

`apps/api/test/native-recovery.test.ts` uses the actual built backend, two isolated accounts and retained real Postgres. For each boundary it records the exact owned PID, actual `SIGKILL` termination, a different restarted PID, equal build hashes, public native snapshots/step history and fixture effects:

| Kill boundary | Before process death | Required recovered observation |
| --- | --- | --- |
| Committed before native start | Intent and stable run ID committed; no native row/start | Same committed run ID starts and saves success; one native row/effect |
| Started before acknowledgment | Native accepted/running; client acknowledgment withheld and lost | Same native identity and real step re-entry, without re-sending the uncertain conversation call |
| Native waiting | Saved `waiting`, completed preceding step and active named native sleep | Native saved progression/terminal outcome on the same ID and graph, not an enqueue receipt mistaken for waiting |
| Effect before step acknowledgment | Fixture SQL effect committed, native step still running | Actual guarded re-entry across different PIDs; inserts `1, 0`, one effect and saved native success |

Each case repeats bounded reconciliation, then performs another real kill/restart and terminal reconciliation without extra runs/effects. Final natural SIGTERM exits 0 inside the shared seven-second budget, with no native budget handles/in-flight hand-off and zero serving connections. Public pool diagnostics and `pg_stat_activity` prove no borrowed client/transaction spans the waits.

Per-boundary fresh-allocation negative controls fail after the actual kill/restart: three reconciliation calls create four native rows where one is required. A separate unguarded-effect negative control saves native `failed` instead of success on re-entry. The initial exploratory naive fixture that could not reach some kill barriers is preserved as setup/non-pass evidence, not counted as the final per-boundary functional red. Stable-ID/guarded corrected cases pass. The two-run aged-budget case kills at approximately 2.8 seconds, restores exactly two permits/four remaining timers, rejects excess and foreign cancellation, then cancels both at their original approximately five-second bound and admits a later replacement. A progressing native sequence uses stable absolute wakeups at four/eight/twelve seconds; after a real kill during its second wait, canonical completed-step history selects the remaining per-wait ceiling while the original total deadline stays ten seconds. It saves canceled at that original total bound and produces no late effect. A fresh-ten-second-on-restart negative control misses that bound. No clock is mocked and no native state is patched.

All fixtures, SQL setup, barriers and control routes are excluded from normal compiler inputs/assets and denied by real Vite serving. No production bootstrap extension was needed: only the separately built composition primes its test bookkeeping before using the unchanged shared entry.
