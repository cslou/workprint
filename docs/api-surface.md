Source of scope: [implementation spec §4](specs/implementation-spec-001.md#4-architecture). Shape source of truth: [`@workprint/contracts`](../packages/contracts/src/index.ts) and its [public DTOs](../packages/contracts/src/models.ts). ## Current delivery and common rules

- Production exposes **only `GET /health`**. Story 4 supplies schemas and named in-process `unavailableApplication` boundaries, not mounted routes or an application client. P1-S5 owns those adapters and HTTP evidence; Phase 2 owns genuine frontend wiring. No table entry below implies a current browser consumer.
- Every application entry requires verified Supabase identity. Boundaries invoke the supplied authenticator **before** closed validation of `{ params, query, body }`. Invalid identity → `unauthenticated`; verifier unavailable → `integration_failure`; malformed shape → `invalid_input`; then real implemented-resource ownership checks must precede `not_implemented`. No product resources exist yet, so no ownership query, invented store, seeded domain data or claimed ownership proof exists here. Functional owners below must supply those checks when they implement resources. Auth itself is qualified separately in [the native record](native-runtime-qualification.md).
- HTTP adapters normalize absent params/query/body to `{}`; GETs carry no JSON body. Query `limit` is an integer 1–100 (omitted means owning implementation's bounded default); cursor is an opaque nonempty string ≤1000 characters. HTTP query decoding belongs to P1-S5, not coercion inside the shared schemas. IDs are opaque nonempty strings ≤200 characters, revisions are nonnegative integers; dates are ISO UTC strings. No caller account/owner, provenance, approval or provider credentials are accepted as envelope fields.
- All objects are closed except the explicitly **domain-owned JSON content and provider-setting values**. `content` is a JSON object, not an implemented Script/reference/storyboard validator. P3-S2/S5 must validate its versioned creative structure using authorized source material before enabling writes; P4-S8 owns provider-setting validation before proposals execute. These extensible data values grant no authority. No private database rows, object keys, native snapshots or stream protocol are DTOs.
- Mutations all require `operationId`. The eventual owner must reconcile identical retries to the original result and reject conflicting payload reuse (`invalid_input`). **No idempotency ledger or successful effect exists now**: valid requests return `not_implemented` on every call, without writes/provider/native work. Reads are effect-free and grant no approval. Do not automatically retry uncertain future mutations.
- One closed error envelope: `{ error: { code, message, details? } }`. Details, if present, contain only `issues?: [{ path: (string|number)[], message }]` and/or `ids?: [id]`; never raw input, upstream errors, SQL, stacks or secrets. Codes/statuses: `unauthenticated`/401, `forbidden`/403, `not_found`/404, `invalid_input`/400, `stale_revision`/409, `superseded`/409, `unsupported`/422, `not_implemented`/501, `integration_failure`/503. These are distinct errors, not success-shaped placeholders. Unknown/malformed envelopes fail schema decoding.
- Foreign/unknown reads use `not_found` to avoid disclosing existence. Functional mutations may use `not_found`/`forbidden` as specified below. No existing resource is made accessible by possessing an ID. Human actions and trusted assistant tools remain separate entry points; shared core logic is not shared actor authority.

### Exact bindings and DTO choices

- `Version`: `{ id, artifactId, kind, revision, createdBy: human|assistant, createdAt, dependencies, content|media }`. Script/reference/storyboard carry JSON `content`; image/video carry safe measured media metadata, **not URLs or private storage keys**. Access URLs use `media`. Version-list entries currently use this same public projection (no private/full-row alternative). Library has no conversation use state.
- `intendedUse` is a structured purpose binding: `{ purpose: script|reference|storyboard|panel_image|shot_video, ...conditional target }`. Reference may carry `role`; Panel image **requires both** `shotId` and `panelId`; Shot video requires `shotId` and forbids Panel/role; script/storyboard accept no target fields. `useVersion` flattens this binding alongside operationId/versionId as specified; returned `use` is `{ id, versionId, binding, state: draft|approved }`. These are shape checks, not proof that a Panel belongs to a Shot or a version matches its purpose.
- Workspace: script is work-or-null; assets are work items; storyboard is `{ work: work|null, shots }`; work is `{ version, use: use|null, state: Draft|Ready }`. Ordered Shots contain stable `shotId`, `order`, optional `intent`, ordered Panels, and `chosenVideoVersionId|null`. Each Panel contains stable `panelId`, order, description, exact reference IDs, candidate image versions and `approvedImageVersionId|null`. Videos are targeted Generation Requests. `activeWork` contains `{ type: generation|export, id, status }`. No latest fallback replaces missing exact IDs; no candidate is implicitly approved.
- Question scope preserves optional exact `versionId`, `proposalId`, `useId`; options are concrete `{ id, label }`. Answers contain **only** operationId/questionRevision/optionId; typed text must be a native ordinary message, leaving the question pending until answered/superseded. Functional P3-S7/P4-S4 enforces recognized human authority, currentness, one pending question, and exactly one approval option for a generation question; schema shape alone cannot establish those facts. Effects are `approval`, `use` or `batch_authority`, never proof that a batch has started.
- Proposal: exact `id/revision/questionId`, purpose, conditional target, provider/model/prompt/settings, candidateCount, ordered `{ versionId, role, order }` inputs, string disclosures, and estimate `{ amount?, currency?, basis: provider|calculated|estimated|unknown }`. `reference_image` requires **only role**, `panel_image` requires **only Shot + Panel**, `shot_video` requires **only Shot**. Generation Requests repeat the same discriminated purpose/target, plus id/batchId/proposalId/status/failureReason?/resultVersionId?/remote/usage?. No returned result selects itself. Native run identities and provider payloads remain private. Remote exposes only taskId?/status? as required by the spec, never credentials or receipts. Usage is an optional safe quantities projection (`unit/amount/basis`, optional cost estimate), not totals or billing authority.
- Generation statuses: queued/submitting/running/succeeded/failed/cancelled. Export statuses: queued/processing/succeeded/failed/cancelled. Export preserves capturedSelectionRevision/current/sources (exact Shot/version/order), compatibility `{ compatible, issues: [{ versionId, message }] }`, failureReason?/outputVersionId?. Export download uses output-version media access. A state machine, stale-input handling, decoding, pricing, order uniqueness, lineage and actual ownership are **not implemented by structural schemas**.
