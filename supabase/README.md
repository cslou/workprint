# Isolated application migrations

This directory owns only the `artifacts` schema. Native tables are created exclusively by the supported `PostgresStore.init()` path; application migrations must never contain native DDL. Supabase's migration ledger is CLI-owned. Seeds and local services are disabled in this config. Do not start, stop, reset, link or reconfigure a Supabase stack from this checkout.

Use only a newly acquired, uniquely owned Postgres fixture from `apps/api/test/postgres.ts`. Its setup role is `wp_setup`, its restricted serving role is `wp_serving`, and its database is `workprint`. Prepare native storage through the existing supported helper and grant native serving access, then apply the application migrations:

```sh
MIGRATION_DATABASE_URL='<private isolated setup URL>' pnpm db:migrate
```

The separate script never alters `scripts/tasks.mjs`. It invokes the pinned workspace Supabase CLI's `db push --db-url` and refuses missing/non-loopback targets, a different setup role/database, supplied URL options, or an unexpected CLI version. It does not execute migration SQL itself. Reapply runs the same CLI command and leaves already applied history unchanged. Only this loopback ephemeral fixture uses `PGSSLMODE=disable`, because it has no TLS listener; this workflow is not a remote/shared deployment migration command. Setup URLs and CLI error arguments are not printed.

Native preparation and migration credentials remain setup-only. Serving receives only its existing `DATABASE_URL`; root start/development tasks already strip `MIGRATION_DATABASE_URL`, and serving configuration rejects it. Application startup does not apply migrations. Serving has schema USAGE and table SELECT/INSERT, not schema CREATE, immutable-version UPDATE/DELETE, ledger access, table ownership or setup-role membership. Database triggers additionally reject version/dependency changes even from the owner. Application validation and owner filters remain necessary; a single trusted backend role is not a per-browser-account database login.

## Dependency rationale

Supabase CLI **2.84.2** is an exact development-only dependency and is checked by the wrapper. It supplies the required supported migration workflow against an explicit isolated URL; a custom SQL migration runner is not an acceptable substitute. The established local CLI version was selected rather than changing stack/runtime cohorts. Its official installer requires the explicit `allowBuilds.supabase: true` permission to obtain the versioned platform binary; no other lifecycle permission or release-age setting is changed.

The CLI's exact `tar` dependency had new advisories during the initial audit. A narrowly scoped `supabase>tar` override pins compatible patched **7.5.21**; the workspace lockfile is generated by pnpm. This affects the development installer, not the application runtime. Re-run frozen install, CLI migration/reapply tests and the audit after dependency changes. The observed patched audit retains only the two already documented backend baseline advisories; those remain NON-PASS, not successes.

The reusable migration and domain tests create and tear down only their own labelled Postgres containers. They do not use a shared stack's application database or a production seed route.
