# Workprint

A chat-first filmmaking workspace: the assistant prepares the work; the creator directs, reviews and chooses.

## Status

Phase 2 delivers the approved React/React Aria shell, navigation and review/input/export components, with frontend consumers for all 19 closed `/v1` operations through `@workprint/api-client`, verified against **one built Mastra backend** backed by Postgres and real Supabase admission. The backend now serves owned saved-work reads and writes, uploads and media access from isolated persistent storage; the question/proposal, generation and export operations still return structured 501 responses. The frontend restores validated saved content and bounded, explicitly activated history/Library pages through the approved consumers. **No completed filmmaking flows are implemented.** Missing prerequisites come only from labelled read-only test compositions; test mounts and fixtures are excluded from production builds. `GET /health` remains public. See the [Sprint 002](docs/sprints/sprint-002.md#final-review) and [Sprint 003](docs/sprints/sprint-003.md#final-review) Final Reviews.

Standard account/session access and owned native create/list/history APIs have scoped implementations below. Native chat sending (P3-S1b/S1c), generation status/cancellation (P3-S8) and export processing (P3-S11–S13) remain unimplemented [Phase 3 work](docs/specs/implementation-spec-001.md). Actual generation/provider execution remains Phase 4. Muse is the intended model family, not a qualified integration.

Sprint 005 was accepted into `phase-3` with recorded gaps carried to the clean-up sprint (not Complete; see its [Final Review](docs/sprints/sprint-005.md#final-review)). It adds owned saved-work reads, manual saves, Storyboard edits with one selection revision per conversation, exact Panel-image and Shot-video choices, private upload coordination through a bounded S3 adapter (image uploads only; video upload is temporarily disabled), Library reuse, and private single-clip playback and download. Storage is verified against the local SeaweedFS emulator; hosted R2 is out of scope until hosted deployment, so no R2 delivery is claimed.

**Private/local development only:** the app-owned entry now authenticates and bounds JSON intake before the pinned adapter can clone/parse a body. Unknown paths reject before intake; admitted bodies are capped at **1 MiB** with a **two-second body-read deadline**. The outstanding B-004 dependency advisory still prevents shared/public deployment; bounded ingress alone does not authorize deployment or native consumers.

| `apps/api/src/mastra/server.ts`, `shutdown.ts` | Shared app-owned entry: official Hono adapter, trusted composition hooks, one loopback listener, workers, startup recovery and one bounded signal-driven drain/shutdown. |

| `apps/api/src/mastra/native-navigation.ts` | Only qualified native thread create/list/read/message reads, with verified-resource ownership and bounded native responses. |
| `test/e2e` | Playwright end-to-end journeys against the real signed-in app, sharing one isolated backend per run. |

Backend ownership reads are declared by `application/`, implemented by `agent/mastra/` through native storage, and supplied by backend `mastra/` composition. Application code imports neither native integration subtree. Ownership has no separate public route; the four implemented saved-work reads consume the collaborator through the application/domain boundary.

Dependency direction: the shell composes features; features use shared `api/` and `ui/`, which do not import features. `api-client` depends on `contracts` and the supported native client; packages never import apps. Browser code/packages cannot import backend or Node modules, and only web may consume `player`. These package/server boundaries, including the framework-free player boundary, are enforced by [dependency-cruiser](.dependency-cruiser.cjs).

## Development

Prerequisites: a working Docker engine, Git/tar for the clean-export smoke, and pnpm **11.28.8** (Corepack can select the version in `package.json`). pnpm downloads the repository-local Node **24.22.1** runtime; no global Node upgrade is needed. Dependency versions are pinned in the [root](package.json), [API](apps/api/package.json) and [web](apps/web/package.json) manifests and [lockfile](pnpm-lock.yaml).

### Amp orbs

`.agents/setup` installs the manifest-pinned pnpm and repository-local Node, frozen-lockfile dependencies, Playwright Chromium and its Debian libraries, and the Docker CLI/daemon. It also caches verified native media tools and immutable fixture images. Amp snapshots these installed assets; warm setup checks reuse them. Use `pnpm exec node` for standalone repository scripts so they use the pinned runtime rather than the orb's global Node.

`.agents/resume` checks Docker and starts the supervised, Unix-socket-only service declared in `.amp/services.yaml` when needed. It installs nothing. Inspect failures with `amp orb service logs docker`; `amp orb services ensure` repairs the declared service. No app, database fixtures, credentials, `.env` file or public portal are created automatically. Existing private configuration is untouched; tests retain ownership of disposable data and teardown.

Quick and standard gates need no private configuration. Deep/integration/browser checks use native Linux x64 or ARM64 media, selected from `apps/api/src/storage/media/pins.ts`; the Docker daemon and cached image must match the host architecture. The sandbox retains `--pull=never`, exact archive/binary verification and its existing isolation/resource limits. No system-FFmpeg fallback or emulation is allowed. Media preflight runs before acquiring the backing stack. Setup caches images; standalone fixtures acquire missing images on demand, never during resume.

Outside an orb, with local Docker ready, run `pnpm exec node scripts/setup-media.mjs` to prepare those same caches. An optional final argument supplies a retained exact archive for offline media acquisition (missing Docker images still require registry access). Media comes from [BtbN's 2026-10-31 month-end build](https://github.com/BtbN/FFmpeg-Builds/releases/tag/autobuild-2026-10-31-12-59), FFmpeg `n8.1.3-27-g8dca1586f4-20261031`, LGPLv3+, with verified SHA-256/size pins for both architectures. Native binaries require glibc ≥2.28 and libgcc; local qualification is not production-distribution clearance. Upstream retains month-end archives for two years, rather than only 14 daily builds; plan a reviewed pin refresh or retained source before that retention ends. Installed snapshots retain the verified bytes. A missing download fails setup rather than upgrading silently.

To verify lifecycle changes, run `.agents/setup` twice and `.agents/resume` twice, timing each run, then run the configured gates. Setup changes become available to future project orbs after they reach the default branch; a local commit alone does not activate them.

### Local development

From the repository root:

```sh
pnpm install --frozen-lockfile
pnpm db:local
```

Keep that terminal open. No prior `pnpm build` is needed: `db:local` reuses the test fixture's dependency-ordered compilation of contracts, api-client and API helpers before starting storage. The development-only helper creates a uniquely labelled, ephemeral Docker Postgres on a loopback-only ephemeral port, creates separate setup/serving roles, runs the supported native initialization through `pnpm db:prepare`, and grants serving DML access. It writes only the database settings to ignored, mode-0600 `outputs/local-database.env`; it refuses to overwrite an existing file. It does not use your Supabase stacks.

In a second terminal:

```sh
SUPABASE_URL=http://127.0.0.1:1 SUPABASE_PUBLISHABLE_KEY=health-only WORKPRINT_ENV_FILE=outputs/local-database.env pnpm dev
```

Root tasks layer their environment: the shell wins, then the file named by `WORKPRINT_ENV_FILE`, then the root `.env` (a value set earlier is never overwritten). So the helper's file supplies the database, and the root `.env` supplies the rest, including the required `DEFAULT_ASSISTANT_MODEL=meta/muse-wonder-1.0` and `META_API_KEY`; the server does not start without them. A named `WORKPRINT_ENV_FILE` that does not exist fails before anything starts. `pnpm build` loads no env file.

These health-only examples explicitly configure an unreachable loopback Auth target: health never calls Auth, while protected application calls cannot authenticate against this target. This is not a token-verification bypass or a working sign-in configuration. For actual admission, supply your separately authorized Supabase URL and publishable/anon key instead.

Open `http://127.0.0.1:5173`; the backend health endpoint is `http://127.0.0.1:4111/health`. `PORT` and `WEB_PORT` override those loopback ports. Stop the apps first, then Ctrl-C the database helper: it stops only its owned container and removes its unchanged environment file. **Fixture data is temporary and is lost on stop.** If the file was edited, the helper preserves it and reports that fact. After an uncatchable host/process kill, inspect the exact `workprint-fixture-<UUID>` container and its matching `workprint.fixture` label before stopping that container; never reset another stack or prune Docker resources broadly.

To build and serve the built apps while that database helper remains open:

```sh
pnpm build
SUPABASE_URL=http://127.0.0.1:1 SUPABASE_PUBLISHABLE_KEY=health-only WORKPRINT_ENV_FILE=outputs/local-database.env pnpm start
```

`pnpm build` compiles backend/shared packages with `tsc` and builds the browser with Vite; it needs no database or private environment file and no longer uses the Mastra CLI. `pnpm start` runs `apps/api/dist/src/mastra/server.js` plus Vite preview (a local verification server, not deployment configuration). `pnpm dev` initially compiles the same entry, then uses TypeScript's built-in watch and Node's `--watch` reload alongside Vite. Mastra Studio/`mastra dev` are intentionally unavailable locally. Browser output is `apps/web/dist/`; backend and separate setup code compile into `apps/api/dist/`. Test helpers compile only into ignored `.test-build/` and are not production compiler inputs or assets.

### Serving lifecycle

The single `Mastra` instance from `createBackend` is served by `@mastra/hono` **1.7.21**, with direct `hono` **4.13.14** and `@hono/node-server` **1.19.17** dependencies for app construction and the one loopback listener. Core/server remain **1.79.0**, pg **1.32.0**. The adapter adds `fetch-to-node` **2.1.0** for its supported custom-route bridge; no replacement transport is authored. OpenAPI stays unset/off. Public health remains `200 { success: true }`. Before native context registration, `ingress.ts` applies narrow CORS/preflight, public health admission, exact catalog default-deny, one online header-Auth verification and bounded JSON intake, in that order. Unknown paths/methods return JSON 404; invalid Auth returns 401 and Auth-service failure returns 503 before any intake. Catalog matching and narrow CORS parsing/decoration are shared with the native compatibility fallback through `admission.ts`. The pinned Node adapter hides GET payloads from WebRequest bodies and skips their cleanup, so ingress checks only transport framing headers (never reads before Auth): body-bearing `GET /health` returns exact 400 `invalid_input` as invalid public-health input; a catalog GET with framing authenticates first, then returns the same 400. Both declared and chunked unfinished GETs are server-closed; ordinary bodyless health stays public 200. Wrong-type/malformed/oversized/over-deadline bodies return exact 400 `invalid_input`, including declared lengths over 1 MiB; exactly 1 MiB is accepted. `body.ts` owns the single 1 MiB/two-second policy used both by intake and application routes. A new raw `Request` carries buffered bytes and the original URL/method/headers/signal through native cloning. A public response-close listener observes disconnect before awaiting Auth, without triggering the adapter's lazy body/signal getter. A transport closed during Auth never dispatches after verification; admitted requests carry combined original/transport cancellation. The temporary listener is removed when middleware settles. The trusted account is held separately from Mastra's replaced RequestContext and copied into it without a second Auth call. Rejections cancel/release the reader, finish the JSON response, then destroy the owned incoming request and close its socket. The two-second timer ends before downstream work; the inherited 180-second general server timeout remains unchanged after native context/programmatic middleware. The terminal JSON 404 and the old middleware's compatibility fallback remain; the supported serving path takes its additive trusted-identity branch.

Startup awaits native `startWorkers()` (legacy `startEventEngine()` fallback). Storage initialization respects `disableInit`; serving still cannot prepare schemas. Workflow recovery runs unless configured `off`; durable-agent recovery runs only for `auto`. Both start concurrently; failures are logged without taking down serving. SIGINT/SIGTERM closes admission and starts **one monotonic seven-second total deadline**, including HTTP, an optional trusted owned-work settlement hook and real `mastra.shutdown()`. HTTP gets at most **two seconds**, with idle sweeps every **100 ms** before remaining connections are force-closed. Native shutdown receives only the remaining budget (also capped by configured drain); a missed total deadline or settlement/shutdown error exits **1**, never false success. A duplicate signal inside **250 ms** is ignored; a later duplicate exits 1.

Deliberate differences from the generated entry: no browser-stream endpoints or WebSocket injection (the previously reachable `/api/agents/:agentId/browser/session` now returns JSON 404); no Studio refresh streams; no usage telemetry startup/synchronization; no private scorer-trace workflow registration. No scorers are configured; trace scoring must revisit that registration before enablement. These omissions do not enable inference. Bounded intake is a separate app-owned guard, not an upstream adapter patch.

### Native conversation ownership foundation

Owned native navigation uses only the four qualified `/memory/threads` create/list/thread/message paths in the existing pre-Mastra catalog. It preserves the verified account/resource rule below, reuses the foundation ownership collaborator and public native storage, and enables no Agent, Send, tools, generic mutation or second store. Official `@mastra/client-js` **1.56.0** read methods run without retries behind the bounded client seam.

`application` receives a read-only `checkOwnedConversation(verifiedAccountId, conversationId)` collaborator. Its native adapter calls `PostgresStore.getStore('memory').getThreadById({ threadId, resourceId })`, then compares `thread.resourceId` exactly with the verified account ID. Foreign and absent threads both return `not_found`; malformed IDs never reach a query, and storage failures return typed `unavailable`. All operations remain Auth-first; saved-work reads and writes, uses, Storyboard edits, uploads and media access use this collaborator, while the question/proposal, generation and export operations remain unavailable.

**Conversation creation rule for Sprint 004:** use the verified Supabase `accountId` unchanged as the native thread's `resourceId` (and the resource identity of its messages). Never use a caller's owner field, conversation ID, email, display name, prefix or normalized substitute. This is native storage identity, not a second conversation table. Before writing the adapter, isolated Postgres on core 1.79.0 / pg 1.32.0 returned the redacted native shape `{ id: string, resourceId: string, title: string, metadata: {}, createdAt: Date, updatedAt: Date }`; the supplied resource identity round-tripped exactly.

`apps/api/test/support/native-conversations.ts` creates native threads and optional messages only for isolated tests through supported storage APIs. Tests own their database and teardown. The helper is not a production compiler input, bundle, asset or route; no seed endpoint is enabled.

The product `OwnedShell` keeps only ephemeral list/selection/history presentation. New video is client-only: it returns to the opening composer and writes nothing. The native thread, whose id is the video id, is created by the first accepted send (Sprint 006). Recents paging, opening, reload and reconnect never create or send. A URL conversation reference restores through verified read-only native requests, not a browser conversation store. Account changes clear old presentation/drafts and the reference; late list/history results cannot replace a newer scope. Load earlier messages preserves the visible anchor. Native history is not Script/workspace material, approval or tool state; the existing unavailable workspace feedback remains truthful.

Automated Auth admission runs against the shared test stack's own GoTrue with disposable synthetic accounts (see below). Any other Auth target requires privately supplied dedicated Supabase Auth configuration and restricted serving credentials. Provisioning/accounts remain outside the product and serving process. Do not substitute a trusted-identity bypass or use an arbitrary shared project. R2, media tooling and real model keys are not prerequisites here.

## Configuration and safety

- `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` are required backend configuration. Supply a publishable or legacy anon key; no service-role/admin credential is needed. HTTPS is required except on loopback, and URLs cannot contain credentials, paths, query strings or fragments. The single integration calls `GET /auth/v1/user` with the bearer token and API key, uses only the verified user `id`, and has a 2-second deadline including response body. Missing/malformed/invalid/expired tokens receive HTTP 401 `unauthenticated`; verifier failures receive HTTP 503 `integration_failure`. Caller owner claims never supply identity.
- Local media qualification is optional and backend-only: supply `MEDIA_TOOLCHAIN_DIRECTORY` and absolute `MEDIA_DOCKER_PATH`, optionally `MEDIA_ARCHIVE_PATH` for the retained exact archive. Missing settings leave verification unavailable; partial, missing or mismatched tools/images fail startup closed, with no download/PATH fallback. The native Mastra shutdown lifecycle owns media termination and storage/database disposal. Local media qualification is not production-distribution clearance.
- Private object storage is optional and backend-only: supply `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` and optional `S3_REGION` (default `auto`). Absent configuration stays unavailable; partial configuration fails closed. HTTP is loopback-only; HTTPS does not authorize cloud calls. Never put these values in browser settings or logs. The owned authenticated emulator uses exact-origin CORS and private generated credentials, not shared storage. Storage access and upload authority/cleanup remain distinct.
- `DATABASE_URL` is serving-only. `MIGRATION_DATABASE_URL` is setup-only; root development/start commands remove it from the native child environment.
- `DEFAULT_ASSISTANT_MODEL` and `META_API_KEY` are required; the server does not start without them. The accepted models are `meta/muse-wonder-1.0` (Muse Wonder, the default since Sprint 014) and `meta/muse-spark-1.3` (Muse Spark), both through Mastra's model router at Meta's registry endpoint; there is no code default, and the key is mapped explicitly from `META_API_KEY`. A failure names only the setting (`Invalid or missing server configuration: <NAME>`), never the value. There is no mode that switches chat off: tests route the same model to a scripted loopback provider with a placeholder key behind the network guard. The key never enters browser configuration, logs or command arguments.
- `MINIMAX_API_KEY` is optional and backend-only. With it, the agent can make videos through MiniMax Video V2; without it the server starts and video generation is unavailable. A malformed key fails startup, naming only the setting. `pnpm live:video` runs the video check against a fake MiniMax; only `pnpm live:video --live` makes one paid call.
- Turn limits: 32 KiB per message, 32,768 output tokens per model call (reasoning included), 100 steps per turn, a 35-minute turn deadline, and a model call fails after 120 s with no data (a stall limit, not a total duration). There are no automatic provider retries and no model fallback. One turn runs per video at a time; a send while one runs is rejected as `busy`, and there is no queue. `pnpm live:chat` runs the chat check against the scripted provider; only `pnpm live:chat --live [--model <id>]` makes a few real model calls (Muse Spark unless another qualified model is named).
- Actual credentials belong only in ignored private files/environment, never browser configuration, prompts or logs. Vite receives no backend environment, does not load dotenv files, and disables automatic `VITE_*` exposure. Its filesystem allowlist contains only the web app, installed dependencies and compiled browser-safe contracts/client exports—not private research or outputs. Backend `VITE_*` settings remain rejected.
- `WORKPRINT_PUBLIC_API_ORIGIN` is the public application-API build/development setting. Supply an explicit HTTPS origin (HTTP only on loopback), with no credentials/path/query/fragment. For local connectivity use `WORKPRINT_PUBLIC_API_ORIGIN=http://127.0.0.1:4111 pnpm build` (or `pnpm dev` with the documented database/Auth configuration). Missing settings preserve credential-free health smoke and render the approved unconfigured Library message; there is no production fallback. Rebuild after changing a built frontend's API origin. Root tasks strip this value from the backend child.
- `WORKPRINT_PUBLIC_SUPABASE_URL` and `WORKPRINT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` are the only additional public build/development settings. Supply both or neither. The URL follows the same origin restrictions; keys must be publishable (`sb_publishable_…`) or legacy `anon`, never secret/service-role/admin credentials. Role inspection validates configuration only, not identity. Vite rejects invalid pairs without printing values; absent settings expose no credential form. Root tasks forward exactly the three public values to Vite and remove them from the serving child. Rebuild after changes. Browser and backend must point at the same separately authorized Auth deployment; never reconfigure shared SMTP/redirects for a test.
- `WORKPRINT_BROWSER_ORIGIN` is a separate optional backend setting, e.g. `http://127.0.0.1:5173`, permitting exactly that browser origin on registered application paths/methods. Unset means cross-origin access is disabled. Only Authorization/Content-Type preflight headers and GET/POST/PATCH are allowed; unqualified native/excluded routes, extra headers and unapproved origins stay denied. No wildcard or credentialed CORS is enabled. This is not deployment or live-call authorization.
- `createConfiguredBrowserClient` composes only the explicit public origin and a supplied token-provider seam; it does not implement login, refresh or a session store. `Library` requires supplied scope and owns read settlement/cancellation; missing scope does not guess an identity. Account/conversation changes invalidate results before effect cleanup, and mutations are never lifecycle effects. Its material renderer is a supplied collaborator for later page composition, not a fake saved catalogue.
- Root commands force Mastra telemetry disabled, offline tooling and explicit dotenv handling. Interrupted or failed compilation stops the pipeline; no later build/setup stage may launch. No inference, paid work, telemetry exporter, test provider or qualification endpoint is registered in production. A separately built test composition adds a protected identity probe using the same backend admission code; no environment flag enables that probe in the production artifact. Credential presence is not call authorization.
- Expected idle Postgres disconnects are logged with a sanitized SQLSTATE, not credentials or raw error payloads. The native pool discards failed idle clients and can replace them on demand. Docker fixture cleanup is registered before acquisition, verifies the preselected name/owner and exact ID, explicitly removes never-started owned containers, and retains both acquisition and cleanup errors if ownership cannot be established.

## Account and session ownership

`apps/web/src/auth/` owns public Auth validation, one persistent official `@supabase/auth-js` **2.118.0** owner, public entry cards and the signed-in account dialog. The SDK alone owns credentials, persistence, PKCE exchange and refresh. Recovery callback parameters are captured only for the supported SDK exchange and immediately removed from the address bar; recovery access never feeds the API token seam. Password update ends recovery through local SDK sign-out and requires fresh sign-in. Sign-in/reset errors do not disclose account existence; uncertain delivery/mutation outcomes never claim nothing happened or automatically repeat work.

`/` is public, with Sign in or Open workspace according to the confirmed account. `/sign-in` is a standalone card; `/app` mounts the workspace only for a confirmed identity. Cold checking/failure renders no workspace DOM or protected reads; explicit retry revalidates through the same owner. Already confirmed refresh retains its workspace and drafts. Returns allow only `/app` and its existing UUID conversation query; legacy root conversation links use the same gate. Backend admission and ownership remain authoritative. Recovery callbacks take precedence and never grant workspace access. Sign-out locks/unmounts immediately; noncredential exit outcome metadata in the existing access fence preserves truthful exit feedback across reload and history navigation, without persisting another session.

The owner stores only presentation and an intent epoch plus a noncredential, same-origin access-fence marker. Password exchange uses an ephemeral official SDK client with persistence, refresh and broadcast disabled; only the sole persistent SDK client publishes through public `setSession` after checking the current intent. A durable noncredential intent revision survives removal of the temporary access fence. Intent changes cancel old controlled user reads; standard Web Locks serialize complete SDK initialization, potentially mutating user validation and explicit session mutations with publication. Recovery is bound to its original intent and online-verified SDK identity, checked again inside the mutation boundary. SDK response bodies are checked before stale user errors can remove shared SDK state. No application credential/session store or custom refresh loop is introduced. Sign-out/switch/expiry fence token access and re-key shell scope immediately; a failed revocation cannot restore old scope on reload. Storage-event receivers do not write another fence, avoiding cross-tab feedback. Successful same-account refresh and ordinary same-account recovery preserve drafts. Although SDK 2.118 can retain a still-valid JWT after proactive rejection, the application immediately fences confirmed terminal refresh errors; retryable outages preserve valid scope. An uncertain logout remains unconfirmed when a later credential-free SDK call is a no-op; only an observed authenticated successful SDK revocation clears it. Failed browser-lock completion, including SDK credential cleanup, is reported through the approved pending/confirmed/unconfirmed storage feedback, with local-only fence retry. An authenticated logout acknowledgement survives subsequent SDK storage exceptions. Recovery settlement uses its post-fence scope and retains the password-update outcome without replaying the update. Unreadable intent storage is not treated as supersession: access is fenced in memory and revocation waits for a verifiable original purpose and SDK identity. Expiry tasks capture only their original scope and account ID, recheck supported SDK expiry, and never persist a stale tab's fence over a newer account. The five additional failure states follow `docs/design/design.md#account-failure-clarification`. No native record is deleted and no command/provider work is replayed. Composer Send remains unavailable; native navigation is a separate scoped consumer of this account/token owner.

Account browser tests use only disposable accounts on the shared test stack's Auth/Mailpit. Standard SDK recovery consumes the delivered link, never an admin-generated replacement. The network observer redacts Auth bodies, callback codes and token-bearing query values before retaining evidence, and consumes exact predeclared operation counts. Account fixtures refuse an occupied frontend port and wait for their own server readiness, rather than accepting an unrelated listener's HTTP 200. Teardown runs every owned cleanup step even when browser context closure fails, preserving all errors. Private fixture records include process, database and network ownership for verified recovery after an aborted worker. Submitted passwords are cleared before awaiting Auth; fixture cleanup closes browser contexts before stopping services so failure snapshots cannot retain credentials. Traces, HAR, video and storage-state captures are disabled for Auth tests.

## Verification

Run the gates through `.checks/regression.sh --tier=quick|standard|deep`: quick on commit, standard on push and on merges into any branch other than `main` or `develop`, deep on merges into `main` or `develop`. [Regression gates](docs/regression-gates.md) lists each tier's checks and budgets. The underlying commands are below; bare `pnpm audit` fails while the reported moderate advisories exist, whereas the gate blocks only on high and critical ones.

```sh
pnpm check
pnpm build
pnpm test:unit
pnpm test:tooling
pnpm test:integration
pnpm exec playwright install chromium
pnpm test:browser
pnpm audit
```

The suite is deliberately small for the MVP (trimmed 2026-11-01). `check` runs strict TypeScript (including the browser journeys), ESLint and dependency-cruiser. Tests live in each package's `test/` folder, never under `src/` (the runner refuses test files there). Unit tests are in `apps/api/test/unit`, `apps/web/test/unit` and `packages/api-client/test/unit`, mirroring `src` paths; `test:unit` runs them without Docker, as does `test:tooling` for the build and dev-task tests in `apps/api/test/tooling`. `test:integration` runs the Docker-backed tests in `apps/api/test/{integration,http}`, whose fixtures live in `apps/api/test/support`; `test` runs all three groups. `test:browser` runs eight end-to-end journeys in the root `test/e2e` (they span the web app, API and stack) against one API and built app: sign-in and sign-out, password recovery, Recents, manual saves, image upload, Library attach, Shot choice and Library video playback. Both Docker-backed commands share one [test stack](#shared-test-stack-test-only) per run; no private fixture files or hosted project are needed.

`WORKPRINT_PREVIEW_PORT` selects the end-to-end app's loopback port (default 4180); use distinct ports and `WORKPRINT_BROWSER_OUTPUT` directories for simultaneous checkouts.

Pixel-comparison screenshot suites were a one-off design-approval aid and have been removed. Approved designs remain as tracked references in `docs/design/`; layout regressions are caught by behavioural browser tests and human QA.
