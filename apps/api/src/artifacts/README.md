# Saved-work domain

`store.ts` owns reads and controlled prerequisite insertion; `writers.ts` owns command effects, and `publication.ts` shares transaction-local version/dependency publication SQL. It receives a pool and the trusted native owned-conversation collaborator; it does not import native storage, the agent or backend bootstrap. Ordinary version origins and every current-use conversation are checked against the supplied account. Only sealed read-only sources in the reserved built-in namespace are globally readable; this is stored server policy, never a caller flag. A missing or foreign resource has the same public failure. Supported isolated test setup calls the same domain entry points, never a seed route.

Versions and dependency edges are immutable, with owner-composite foreign keys and distinct revisions. Conversation uses are separate from Library membership: an approved use pins its exact version, while a newer saved version can remain in Library without replacing it. Unavailable producers are not synthesized; selection revision starts at zero and advances only on saved Shot-order or Shot-video choice changes. Text/planning persistence is enabled. Image upload persistence is available only behind the guarded inspection capability; explicit qualified local-tool configuration supplies the real verifier; absent configuration cannot publish. User video uploads are temporarily denied regardless of configuration. No real built-in examples/catalog ships. Composition registers human saves, Storyboard edits and exact Script/reference/Storyboard/Panel-image/Shot-video uses; agent producers remain unavailable.

`content.ts` validates closed, schema-versioned content before insertion and before public projection. Shared pure shapes in `packages/contracts/src/saved-content.ts` let consumers read supported fields without interpreting arbitrary JSON. The operation inventory is unchanged. Version DTOs have only the approved optional server-derived `builtIn` boolean, matching Library naming; absence means ordinary presentation, never authority to bypass ownership or write checks.

## Existing-record command writes

`createArtifactWriters()` returns separate immutable human and assistant capabilities. Composition supplies only the human capability to authenticated `saveVersion`; a future assistant binding receives only the draft capability. Producer/approval flags are not request fields. Both writers authorize the current conversation, base origin and exact dependencies through the trusted collaborator before entering SQL. Initial authoring/import is unsupported: artifact and expected latest base are required.

Human saves preserve existing structure, order and stable identities. Reference saves may change description and exact image associations together: dependencies must match the associated images, each image is origin-authorized and has a protected verified-media pointer, and the original expected base still fences the atomic save. Other kinds retain text-only/exact-dependency rules. An intended use must be the exact existing use of that artifact in the conversation. Its origin is authorized before SQL, and its identity/version are rechecked under lock. Ambiguous matching reference bindings fail closed rather than choosing an arbitrary use. Planning promotion also preserves the currently used plan's structure/dependencies, so a text save cannot approve an intervening reordered assistant draft and bypass later selection-revision rules. Assistant drafts never move uses or record human changes. Saves without intended use do not invent decisions.

A short transaction serializes the trusted owner/conversation/command/operation identity, rechecks a canonical payload hash, checks the latest artifact base and commits publication, immutable version/dependencies, optional exact approved use, immutable result and manual-change journal together. Identical retries return that original result without reapplying use effects, even after later decisions. Conflicting payload reuse is invalid. The journal retains the edited base and previous exact use version separately; reads do not consume changes. No native turn, provider call, native wait or external collaborator runs inside SQL.

## Human exact-version reuse

`createVersionUses()` supplies a human-only capability for owned Script, reference, Storyboard, Panel-image and Shot-video uses. It authorizes the target conversation and exact version's native origin before SQL; reference use also accepts owned saved images/videos without granting a Shot/Panel choice. A short owner-serialized transaction updates only the matching purpose/role/artifact use, preserves independent conversation uses and records an immutable command result. It creates no Artifact Version, object copy or automatic latest pin; only a Storyboard use that changes the Shot order, or a changed Shot-video choice, advances the selection revision. Identical retries return the original result without reapplying a later decision; conflicting payload reuse fails. New associations respect the existing100-use workspace bound.

Read-only source fixtures are sealed only by the isolated setup role; no production seed endpoint, examples asset or Examples switch is added. SQL denies new versions/dependencies or unsealing of sealed content, and serving privileges cannot forge the built-in flag. A human use or dependency retains its own owner while a server-stamped source-owner foreign key points to the same immutable source version, never a copy. Public artifact identities are globally unique to keep owned/global history and Library references unambiguous. Native ownership still applies to all ordinary foreign content.

Library cursors freeze both the requesting owner's publication counter and the reserved source counter. Sealing receives its own counter stamp, so a source sealed after the first page cannot enter an existing window. The optional DTO flag survives workspace/history reloads and private media access remains gated by the exact authorized version and protected source pointer. Human and assistant content writers reject sealed bases independently of presentation metadata.

The web Library inspection/recovery and reference-edit consumers use these capabilities; `library-reuse.spec.ts` and `library-media.spec.ts` exercise them against the real backend.

## Storyboard edits and selection revision

`selection.ts` owns one monotonic selection revision per conversation in `artifacts.selection_revisions`. It is artifacts-owned metadata keyed by native identity, not a conversation store. Zero means no Shot-order change was ever saved. SQL lets the serving role advance it only by exactly one and never rewind or delete it. Future export capture reads this value.

`createStoryboardEdits()` supplies the human `editStoryboard` capability. It edits only the existing Shots and Panels of the conversation's used Storyboard: the Shot and Panel identity sets must match exactly, orders must stay distinct, and references must be origin-authorized exact reference versions. The expected base must be the used version and the artifact's latest. One transaction publishes the version, moves the use, advances the revision when the Shot sequence changed, and writes the immutable command result and change journal. Retries return the original result; the same operation identity with another payload is rejected. Description-only edits leave the revision unchanged. Using a Storyboard version whose Shot order differs (`useVersion`) also advances it. Generic manual saves stay text-only, so they cannot bypass the revision.

Every human save, edit and exact-use decision journals `affected_version_ids` (`manual_changes` or `use_changes`, which also records the previous version and its owner, equal to the new version on a re-use): the Panel images and Shot videos bound to Shots whose plan changed, siblings included. For upstream Script/reference saves, the journal also names the dependent used versions and the Panel images of every Shot that cites the upstream version; a source Script change counts every Shot. Changes require revalidation. Nothing is regenerated, rewritten, repinned or erased, and reads never consume the journal.

Panel-image and Shot-video `useVersion` bind an image or video version only to an existing Panel or Shot of the used Storyboard, fenced against a concurrent Storyboard change. Uploaded versions stay draft candidates, and the workspace projects every bound version as a candidate. Approving one demotes only that target's earlier approval back to a candidate; a partial unique index keeps at most one approved choice per target. A Panel-image approval leaves the selection revision unchanged. A changed Shot-video choice advances it in the same transaction, and re-choosing the current version does not. Re-uses journal the current version as their previous version.

## Private upload coordination

`uploads/records.ts` owns immutable request/confirmation identities and short SQL lease/reservation phases; `coordinator.ts` owns the admitted bounded request; `completion.ts` commits visibility; `cleanup.ts` performs explicit bounded cleanup. `policy.ts` validates MIME/size/kind and exact existing Shot/Panel targets. Native ownership and target-origin authorization finish outside SQL, as do all storage and inspection waits. Composition supplies private S3 mechanics, never caller ownership/producer flags.

Request grants bind original metadata, issue/expiry, exact length/type and a server-owned staging key. Identical retries retain that identity; conflicting reuse fails. Confirmation binds its operation to the stored upload/conversation, serializes attempts with a 60-second lease and returns the immutable original result after success without reapplying later decisions. Unsupported, foreign, missing, mismatched and expired uploads remain unusable. Current upload admission is JPEG/PNG images only, at most 10 MiB and 4096 × 4096 pixels after verification. The lower-level 100 MiB video transport/storage/SQL ceiling is not permission to upload video. Admission is not media qualification.

**Video upload admission is temporarily closed.** After ordinary native ownership/target-origin authorization, `policy.ts` denies video requests, including old authorization identities. Confirmation rejects stored video rows before claiming an operation, replaying a cached result or performing storage/inspection work. Atomic completion repeats the image-only check under the existing owner-first lease lock. No environment or collaborator flag can re-enable video. Signed grants already issued remain replayable until expiry; denial is not revocation, deletion or rollback. The conflicting-MP4-sample-table validation defect remains deferred and unqualified; re-enablement needs separate authorization and independent verification.

**Image verification is explicit and fail-closed.** Without media configuration, confirmation still returns `not_implemented: Media verification is not available`, publishing nothing. With the exact qualified local toolchain, bounded real inspection now composes into the built backend; real PG/S3/native image tests prove JPEG/PNG publication and exact-version private readback. Prior video decoder fixtures are isolated lower-level evidence, not current user-upload qualification. Synthetic inspection collaborators prove coordination only, not decoding. A valid inspection result can publish only its captured byte snapshot and copied poster, under unique per-attempt immutable keys distinct from replayable staging. Version/dependencies, private pointer/hash, protected references, draft intended-use link and original result commit together. Technical success never approves work or chooses a Shot video; selection revision is unchanged. Private object keys never enter public version DTOs.

Private `media` reads first authorize the exact ordinary native origin or sealed read-only source, then resolve only that version's protected immutable private pointers. The service signs source/poster GETs for60seconds outside SQL; API responses use no-store and private keys never enter version DTOs. URLs are replayable bearer capabilities until expiry; scope changes cannot revoke them. Browser video playback remains unqualified in this slice.

Owner-scoped object references are reserved before writes and survive storage uncertainty or SQL rollback. Unknown attempts use new keys. Cleanup excludes referenced/protected objects, claims a separate lease, handles at most four unprotected references in pairs outside SQL, and records failures. It never deletes reference tombstones: even successful deletion cannot revoke an issued PUT or prevent an admitted late write. No Artifact deletion endpoint or background scheduler is added. See `../storage/README.md` for service provenance, bounds and actual bearer-URL replay semantics.

## Bounds and cursors

Content is at most 256 KiB; declarations additionally bound events, names, Shots, Panels and exact dependencies. Pages default to 20, with the existing contract's 1–100 range, but their serialized UTF-8 JSON also stays within 1 MiB. A byte-limited page's cursor follows the last emitted item, never the first omitted item. The shared transport keeps its 1 MiB bound for other operations/errors; successful workspace reads alone have an explicit 64 MiB aggregate budget. Workspace retains its existing 100-use bound, enough room for every valid full-content use, dependency/use metadata and the duplicated storyboard projection; the server checks the final serialized aggregate as well. Large valid records remain available through all three read surfaces and exact-version reads.

History freezes its maximum revision. Library freezes an internal per-owner publication revision, not wall-clock visibility. Every publisher acquires the owner `publication_counters` lock before Artifact or intended-use locks, then increments the counter and inserts its version in one bounded transaction. Upload completion takes that same owner lock before upload/target/reference locks and rechecks the current lease and exact target inside that transaction; concurrent manual Save cannot invert this order. Request/claim/cleanup phases never acquire a later publication lock. The first page reads that owner row FOR SHARE: it waits for an already publishing transaction and fences later writers until the page's SQL completes. Continuations select the latest version per artifact at that publication revision, so delayed commits and clock adjustments cannot change membership. Existing immutable versions receive publication zero through additive DDL, without changing content. This metadata is unrelated to conversation selection revision or approval. Exact microsecond timestamps remain immutable ordering keys only.

Cursors are signed with a process-local random key and bind account, operation, resource/filter and page size. They are bounded and reject tampering or scope changes. Restart invalidates old cursors explicitly; the consumer must begin a new read rather than silently reusing a cursor. No application cursor secret or private database field is added to a browser contract.

Database transaction mechanics live in `db/transaction.ts`: 3-second statements, 1-second idle-in-transaction timeout and an 8-second wall deadline which destroys the checked-out connection and rolls back its open transaction. Native/provider calls stay outside the transaction. The serving pool is supplied by composition and remains bounded there. Application-role validation includes ownership and database/application-schema CREATE privileges for every SET-reachable role, not only immediately inherited grants.
